Start here

What it is

A skill is a folder of instructions and files that Claude reads when a task needs it. This one teaches Claude to build lesson decks: slide-style web pages that explain a topic step by step, like a good teacher at a notebook or a blackboard.

You describe what you want to learn or present. Claude asks a few short questions, plans the lesson, fills slides from a ready-made library, checks the file, and hands you one .html file. Double-click it and it opens in your browser. Send it to anyone; it needs nothing else installed.

One file, any device

All styles, scripts and drawings live inside the file. It runs in any modern browser, on a laptop or a phone, with keyboard, mouse or swipe.

Hand-drawn and calm

The Sketchbook look: ruled paper or a chalkboard, wobbly ink frames, sticky notes and drawings that draw themselves. No neon, no clutter.

Built to teach

Teaching decks open with a challenge, explain each idea with a picture, its "why" and a real use, then return to the challenge and end with questions.

Arabic or English

Right-to-left Arabic or left-to-right English. Fonts, layout, arrow keys and swipes all follow the language you choose.

43 components

Covers, maps, timelines, comparisons, code windows, charts, steppers, sliders, quizzes and more, each matched to a "teaching job".

Checked before delivery

A small Python validator catches broken decks: two active slides, a missing engine, a wrong board, a widget that would flip slides while you drag it.

What it is notIt does not make PowerPoint files (use a .pptx skill for that). It makes web pages. The decks look like slides, but they are HTML: you can host them anywhere, including GitHub Pages.
Setup · 2 minutes

Install

The skill is the folder lesson-deck-builder/ inside this repository. Put that folder where Claude looks for skills.

Option A — Claude Code (all your projects)

Clone the repository, then copy the skill folder into your personal skills folder, ~/.claude/skills/.

macOS · Linux · Git Bash
git clone https://github.com/MstrPxl/lesson-deck-builder.git
mkdir -p ~/.claude/skills
cp -r lesson-deck-builder/lesson-deck-builder ~/.claude/skills/
Windows · PowerShell
git clone https://github.com/MstrPxl/lesson-deck-builder.git
New-Item -ItemType Directory -Force "$HOME\.claude\skills" | Out-Null
Copy-Item -Recurse lesson-deck-builder\lesson-deck-builder "$HOME\.claude\skills\"

You should now have ~/.claude/skills/lesson-deck-builder/SKILL.md. Start a new Claude Code session and the skill is ready.

Option B — Claude Code (one project only)

Copy the same folder into the project instead: <your-project>/.claude/skills/lesson-deck-builder/. Anyone who clones that project gets the skill too.

Option C — Claude apps (claude.ai, desktop)

  1. Download lesson-deck-builder.zip from the latest release. (Or zip the lesson-deck-builder/ folder yourself: the zip must contain that folder, with SKILL.md inside it.)
  2. In Claude, open Settings → Capabilities, make sure code execution is on, and upload the zip under Skills.
  3. Start a new chat and ask for a lesson. In the apps the skill runs in chat mode: one complete deck per request.

Check that it works

In Claude Code, type /lesson-deck-builder (the skill also starts by itself when you ask for "slides", "a deck", "a lesson" or "a visual walkthrough"). Claude should answer with questions about your topic, not with a deck. That is correct: the questions come first.

You need

  • Claude Code, or a Claude app with skills enabled
  • A modern browser to open decks

Recommended

  • Python 3, so Claude can run the validator
  • Git, for repo mode (Claude commits each lesson)

To update

  • git pull in your clone, then copy the folder again (replace the old one)
Quick start

Your first deck

Just ask in plain words. Any of these works:

Teaching deck

"Make me slides explaining how vaccines work, for someone with no science background."

Presentation

"Build a short deck that introduces our new note-taking app to the team."

Learning journey

"I want to learn machine learning from zero. Start a learning path for me." (best in Claude Code, inside a folder)

A typical conversation

  1. You ask

    You/lesson-deck-builder Make slides explaining how vaccines work.

  2. Claude maps the topic and asks you to confirm it

    ClaudeHere are the nearby topics: how a vaccine trains your immune system · the main vaccine types · how vaccines are tested · herd immunity. I'll restate your aim: "understand how one shot teaches the body to fight a germ it has never met". Is that right?

  3. Claude asks the canvas and the language

    ClaudeCanvas? I suggest Paper (bright, good for daytime reading) · or Chalkboard. And: Arabic or English?

  4. A short intake

    ClaudeWho is it for (complete beginner · generally informed · expert), and how long (≈10 · 20 · 30 min)?

  5. Claude plans, builds and checks

    It sketches the slide list, fills slides from the component library, and runs validate.py.

  6. You get one file

    vaccines.html. Open it in a browser; use the arrow keys, the Prev/Next buttons, or swipe. Ask for changes any time: "make it chalkboard", "shorter", "add a slide on boosters".

Save time: anything you say up front is not asked again. "An English teaching deck on vaccines, paper canvas, beginners, 15 minutes" skips the language, canvas and intake questions. The topic is still confirmed in one line, because a wrong topic spoils every slide after it.

  Under the hood
  
How a session goes

  
Claude follows the same steps every time. Knowing them helps you answer quickly and know what to expect.

  
    
    
  1. Detect the environment
    Repo mode (Claude Code, inside a folder) or chat mode (the Claude apps). It changes where lessons and notes are kept. More below.
    2. 
    
  2. The topic conversation (required)
    Every new learning journey starts here. Claude assumes you know nothing, lists the topics near what you said (with one plain line each), and asks you to confirm one topic or one exact learning aim. Even a precise request gets restated and confirmed. Nothing is built before you say yes.
    3. 
    
  3. The canvas gate (required)
    Paper or chalkboard; on the chalkboard, which of the six boards. Claude suggests one with a one-line reason, always shows the full menu, and never picks for you. See the boards.
    4. 
    
  4. The language (required)
    "Arabic or English?" Asked every time unless you already said it. It sets direction, fonts, button labels and arrow keys.
    5. 
    
  5. Scope (broad subjects only)
    If you could spend weeks on the subject ("DevOps", "personal finance"), Claude offers three ways in: an Overview deck (at most ~30 minutes), a Roadmap + Lesson 1, or a Deep dive on one subtopic. Narrow topics skip this.
    6. 
    
  6. Intake
    One quick round: the angle, the audience level (default: "a newcomer gains real understanding"), and the length (default ≈20 minutes).
    7. 
    
  7. Plan the outline
    Claude chooses the arc (teaching or presentation), turns the time budget into a slide count, and names each slide's teaching job before choosing its component.
    8. 
    
  8. Set up from the template
    Copies assets/template.html, sets dir/lang, fonts, nav labels and the canvas attributes. The engine script is never edited.
    9. 
    
  9. Build the slides
    A visual on every slide that earns one, text in HTML and shapes in SVG, staggered entrances, logical CSS properties so both directions mirror correctly, one idea per slide.
    10. 
    
  10. Validate, then present
    Runs scripts/validate.py, fixes what it flags, and delivers the file with a short note: what was made, how to move through it, and what you can ask to change.
    11. 
  







  Decided once, early
  
Two kinds of deck

  

    

      Teaching deck
      
So you can do or understand something new

      
Lessons, explainers, tutorials, every lesson of a learning path. Uses the teaching arc:

      
Cover›Opening challenge›Ground the newcomer›Map›One idea per slide›Challenge revisited›Recap as "you can now…"›Questions + answer box›Closing

    

    

      Presentation deck
      
To inform or persuade

      
A pitch, a product intro, a showcase, a report. Uses the classic arc, with no challenge and no questions:

      
Cover›Ground›Map›One idea per slide›Transitions›Recap flow›Closing

    

  

  
If your request could be either, Claude asks one question. When a deck explains a concept and nobody said otherwise, it is treated as a teaching deck.







  The look
  
Canvases & boards

  
There is one style, Sketchbook, on two canvases: bright paper, or a chalkboard in one of six boards. Click a card to repaint this whole page with it (the dots in the top bar do the same).


  

    
    
    
    
    
    
    
  


  
One attribute pair decides it

  
In a deck, the canvas is set on the <html> tag and every colour follows. This page right now is:

  
deck.html
<html data-canvas="paper">

  
data-canvas="chalkboard" without a data-board gives the default board, Slate re-inked. Never hand-edit a board's colours inside a deck: pick a board.


  

    
Three pens
Every canvas has pen a (the main emphasis), pen b and pen c (they link parts of a figure). One dominant pen and quiet supports, never a rainbow.

    
Tuned for long reading
Boards are dark but coloured, never black. Chalk is warm off-white, never pure white (it blurs on dark grounds). Body text reaches about APCA Lc 80 on all six boards; pens use medium saturation so they don't "vibrate".

    
Paper objects stay paper
Sticky notes, tape, index cards and gloss cards keep their paper colours on every board, like real paper pinned to a blackboard. Look at the notes on this page in chalkboard mode.

  

  
The gate: Claude always asks the canvas before building, suggests one with a reason (paper by default; chalkboard for night or long screen reading, or if you chose it before), and lists every option. In a lesson series it asks once and remembers. The older looks (Playroom, Nocturne, Terra, Classic) were retired in v1.3; their mechanics live on in components §32.

  Pedagogy
  
The teaching method

  
Teaching decks are designed to turn information shown into capability gained. Four ideas do most of the work.


  
1 · Attempt before instruction

  
Right after the cover, the reader meets a real problem and commits to an answer before any teaching. People learn most from the gap between what they expected and what turned out true. The problem is pitched attemptable but uncertain: you should have a guess and not be sure of it. At the end, the deck returns to the exact same problem (never a similar one) and solves it with what was just taught.


  
2 · The click trio

  
Every load-bearing idea gets all three, woven together. Two out of three is a definition, not understanding.

  

    
Structure
A picture
A diagram, flow, cards, mockup or comparison that shows the shape of the idea.

    
Mechanism
The why
Not what it does: why it works. The mechanism explains the picture.

    
Application
A real use
A real scenario where the idea visibly matters. The application proves the mechanism.

  


  
3 · Close every loop inside the deck

  
Each teaching deck delivers at least one complete, demonstrated capability in one sitting. "More next time" with no win is a failure: the content is split across decks rather than the payoff postponed. The recap is phrased as capabilities: "you can now…".


  
4 · Feedback is data, never judgment

  
A wrong answer gets the mechanism-level reason right away and a chance to apply it again. No scolding, no "unfortunately", no padding. And progress is always visible: roadmaps mark finished steps, and a concept missed last time and solved now is named on the slide.


  
The calm voice

  

    
  • Calm, not techy, not naive. Warm, plain, short sentences.
  • Zero prior knowledge unless told otherwise. Define a word before using it.
  • What and why before how.

    
  • One promise per deck. The cover promises; the closing pays it off.
  • Respect the reader's time. Fit the budget; brevity is part of the calm.
  • Visual-first. A text-only slide is a missed chance.

  







  Teaching decks
  
Questions & the adaptive loop

  
Every teaching deck ends with a short question set and a copyable answer box. In a series, this is how the next lesson knows what to build on.


  

    

      
In the deck

      
    
        
  • A few multiple-choice questions plus 1–2 open questions on the load-bearing ideas.
    • 
        
  • 1–2 stretch questions, tagged [stretch]: one step beyond what was taught. Missing them is expected and useful.
    • 
        
  • A final answer box: an editable text area holding every question with space for your answers. Type in it freely: arrow keys and Space don't flip slides while you type.
    • 
      

    

    

      
After you paste it back

      
    
        
  1. Claude updates the notes file (NOTES.md) with what your answers show, each point tagged with the question that produced it.
    2. 
        
  2. Claude answers your answers: for each miss, the reason at the mechanism level.
    3. 
      

      
Paste the box into the chat even if you don't want a new lesson yet.

    

  


  
How the next lesson adapts

  

    
    
      
  • Earlier misses are re-tested early, in new clothing: same idea, different surface. A gap stays open until a later question closes it.
    • 
      
  • Wins are named: "missed last lesson — solved now".
    • 
      
  • Content is personalized (examples, analogies, depth) from the notes.
    • 
    

    
    
      
  • Stretch misses are not gaps. A missed stretch question becomes the next lesson's opening challenge; repeated misses on core questions mean re-teach.
    • 
      
  • Answers never change the roadmap on their own. Only a gap seen across two or more lessons may lead to a proposal ("Want a short preparation deck on X?"), applied only after your explicit yes.
    • 
    

  


  
The notes file

  
NOTES.md is written by Claude and read before every lesson. It stays small: a header (subject, roadmap version, date), a live picture (active gaps with the question that found them and the lesson that will re-test them, strengths, what kinds of explanation landed), a per-lesson log of a few lines each, and closed gaps. Single data points only tune tone and examples; only repeated patterns can justify a proposal.

Repo mode layout

  
On a new journey Claude creates only what is missing, and never touches files that aren't its own:

  
docs/
  TOPIC.md        # confirmed topic + aim (output of the topic conversation)
  ROADMAP.md      # the living roadmap: readable path + spec JSON + changelog
  NOTES.md        # cumulative learner notes
lessons/
  00-roadmap.html # the roadmap deck
  01-<step>.html  # one deck per lesson
answers/
  lesson-01.txt   # every pasted answer block, saved word for word

  
If the folder is a git repository, Claude commits after each artifact ("lesson 03: transformers — attention", "notes: lesson 02 answers").


  
Scope: narrow topic or broad subject?

  
Rule of thumb: could a person spend weeks learning this? If not, it's narrow: one deck. If yes, you choose:

  

    
Overview
One thorough deck of the whole subject from above. A complete lesson, not a teaser; 30 minutes at most.

    
Roadmap + Lesson 1
A researched learning path as its own deck, then the first lesson. Best in repo mode.

    
Deep dive
You narrow to one subtopic, and it becomes the whole deck.

  


  
Roadmap mode, step by step

  
    
    
  1. Shape the journey
    2–3 quick questions: hands-on · theory-first · balanced; with or without a business lens; job-ready · solid mental model · general literacy. These change emphasis and order, never correctness: no load-bearing step is dropped.
    2. 
    
  2. Research the path
    Real web searches, so the order is right and nothing is outdated or missing. This is research about what to learn and in what order; deep research on each subject waits for its lesson.
    3. 
    
  3. Roadmap deck + spec
    lessons/00-roadmap.html shows every phase, why it's there and how it connects. The machine-readable spec goes in docs/ROADMAP.md (repo mode) or a hidden comment in the deck (chat mode).
    4. 
    
  4. Lesson 1
    Introduction, big picture and why, with a roadmap slide near the front: current step highlighted, finished steps marked.
    5. 
    
  5. Every later lesson
    Load the roadmap → read NOTES.md (save any new answer block first) → re-check the roadmap is still current → propose a change only if the notes justify it → research and build the lesson, personalized → write the state back and commit.
    6. 
  

  
ROADMAP-SPEC (inside docs/ROADMAP.md)


{"subject":"Machine learning","version":2,"updated":"2026-10-16",
 "shape":{"style":"balanced","business":"no","destination":"working mental model"},
 "steps":[
   {"n":1,"title":"What learning from data means","goal":"…","volatility":"solid",
    "research":"angles, sources and freshness checks to run when building this lesson"},
   {"n":4,"title":"Tooling: notebooks and libraries","goal":"…","volatility":"fast","research":"…"}],
 "changelog":[{"v":2,"date":"2026-10-16","cause":"research","change":"library X replaced Y as the common default"}]}

  
Why volatility? Lessons are often taken days or weeks apart, and fields move. Before every lesson Claude re-checks the roadmap: "fast" steps (tools, practices) get re-researched, "solid" steps (fundamentals) a light check. Every change bumps version and adds a changelog entry whose cause is either research (applied by Claude) or approved-proposal (applied only after your yes).







  Engine v2
  
The slide engine

  
Every deck carries the same small script (no libraries). It is copied from the template and never edited; new behaviour goes after it.


  
Moving through a deck

  

    
ActionEnglish (LTR)Arabic (RTL)

    
      
Next (or next build step)→ ↓ Space PageDown · swipe left · Next ›← ↓ Space PageDown · swipe right · التالي ›

      
Previous (or undo a build step)← ↑ PageUp · swipe right · ‹ Prev→ ↑ PageUp · swipe left · ‹ السابق

      
First / last slideHome / End · or click a dot under the slide

    
  

  
A progress bar and a slide counter show where you are. Keys and swipes are ignored while you type in a field (the answer box) or work a widget marked data-capture (sliders, drag figures).


  
Anatomy of a slide

  
between the BEGIN/END SLIDES markers


<!-- the first slide, and only the first, is "slide active" -->
<section class="slide active"> … cover … </section>

<section class="slide">
  <!-- .reveal: animates in when the slide opens; --d staggers it -->
  <h2 class="reveal" style="--d:.1s">How a request finds a server</h2>

  <!-- data-build: appears one key-press at a time before the page turns -->
  <div data-build="1">1. Your browser asks a resolver.</div>
  <div data-build="2">2. The resolver asks the root.</div>
  <div data-build="3">3. The answer comes back.</div>

  <!-- data-capture: the engine leaves keys and swipes here alone -->
  <input type="range" data-capture>
</section>


  

    
Builds
    
      
  • data-build="0..n" reveals parts one press at a time.
    • 
      
  • Going back un-builds; arriving back at a slide shows it fully built.
    • 
      
  • data-builds="n" on a slide declares steps for a widget that listens to builds.
    • 
      
  • Never put data-build and .reveal on the same element.
    • 
    

    
Events for components

      
The engine fires two events on the slide element:

      
  • slideenter — the slide was opened (detail.from)
  • build — a build step changed (detail.step, detail.of)

    

  

  
component code goes after the engine, in the same <script>


const s = document.querySelector('#dns-slide');
s.addEventListener('slideenter', () => startDrawing(s));
s.addEventListener('build', e => moveToken(e.detail.step, e.detail.of));

  
No storage. Decks never use localStorage or sessionStorage; all state lives in memory, so a reload starts fresh.

  references/style-system.md
  
Style laws

  
Five laws apply to every deck. They keep decks calm, readable and consistent.

  

    
Law 1
Depth never moves the scene
Hover or tap content may appear only in one of four ways, and nothing unrelated may shift:
  • Reserved flow — space is kept for it inside a fixed box.
  • Fixed tray — content swaps inside a constant-size, scrolling area.
  • Overlay — it floats above, out of the layout (anchor positioning).
  • Final-geometry — it grows straight to sizes measured in advance.

    
Law 2
Skeleton ≠ skin
Behaviours (stepper, lab, journey, spotlight) are reusable. Drawings are not: each topic gets its own picture from a scene brief — pick the subject that best embodies the mechanism, draw it in the stroke vocabulary, map lesson states to scene states, write captions for that skin. Never reuse an exemplar's subject.

    
Law 3
One coordinate system per figure
Everything that moves in a figure lives inside its own SVG. Static labels may be HTML pinned in the figure's units (a label is not an actor), but never HTML floating over an SVG scene.

    
Law 4
One motion law
Draw-in strokes and slight rotations, easing cubic-bezier(.2,.7,.2,1), about 0.5 s. One sanctioned exception: line boil (§31), one element per slide.

    
Law 5
Little text, louder message
The always-visible layer carries one idea in few words. Everything else is depth (Law 1) or a visual.

    
The look, in short
  • Paper, not white; board, not black. Ink, not black; chalk, not white.
  • Wobbly frames, tape, sticky notes, long soft shadows.
  • No neon, glow, glass, glossy shadows, gradient surfaces, emoji, or purple-on-white "AI slop".
  • Generous whitespace; every slide fits the screen.

  

  
Drawing vocabularies

  
Ways to represent a mechanism, kept from the retired styles and drawn in ink or chalk:

  

    
Blocks and flows
Entities as nodes, processes as a token on a route, quantities as chips or a gauge, categories as zones.

    
Light and energy
Beams, pulses, orbits, signals: decay as a fading pulse, feedback as an orbit, limited capacity as one shared lamp. Matte, never glowing.

    
Objects that enact it
A path that stays open when walked; a tree that bears more after pruning.

  

  
The style file also maps eight content categories (definitional, process, intuition, comparison, narrative, code, thesis, check) to their visible layer, depth mechanic and signature component, and ends with a pre-ship checklist every deck is graded against.







  references/design-system.md
  
Length budget

  
A reader spends about 60–90 seconds per slide. Claude turns your time budget into a slide count and stops there; if the topic needs more, each slide gets tighter, not the deck longer.

  

    
Reading timeSlides (with cover and closing)

    
≈ 10 min8–10
≈ 20 min (default)14–16
≈ 30 min16–20

  

  
In teaching decks, the opening challenge, the challenge revisited and the question set count inside this budget: they replace content slides, they are never added on top.







  scripts/
  
Validator & scripts

  
Two small Python 3 scripts, no packages to install.


  
validate.py — check a finished deck

  
terminal


python lesson-deck-builder/scripts/validate.py examples/isy-05-cryptography.html

  
output


slides: 30   ·   implied reading time ≈ 30–45 min
⚠ more than 20 slides — likely over a 30-minute calm budget; consider tightening
✓ clean.

  
✗ lines are problems (exit code 1); ⚠ lines are notes. It checks:

  

    
    
      
  • Exactly one <html>, <body> and <script>; balanced <style> tags
    • 
      
  • Exactly one slide with class="slide active"
    • 
      
  • No element with a duplicated style= attribute
    • 
      
  • A Google Fonts link is present
    • 
      
  • The engine is present, is v2 (builds + data-capture) and has the typing guard
    • 
      
  • The grain/dust is a tiled image, not a live full-screen SVG filter
    • 
    

    
    
      
  • Components that read --k-* bridge tokens have them defined
    • 
      
  • No element is both .reveal and data-build; scrubbers have data-capture
    • 
      
  • At most one .live element per slide; Arabic uses Playpen Sans Arabic 800
    • 
      
  • data-canvas / data-board are valid and their colours exist in the file
    • 
      
  • Fonts from retired styles; slide count and implied reading time
    • 
    

  

  
HTML comments are stripped before checking, so notes and records inside comments never cause false alarms.

  SKILL.md
  
Hard rules

  
Failure modes the skill always avoids. Useful when you edit a deck by hand, or review one.

  

    
    
      
  • No deck before the topic is confirmed, the canvas (and board) chosen, and the language known.
    • 
      
  • Never edit the engine part of the script; add code after it.
    • 
      
  • One active slide; no duplicated style=.
    • 
      
  • No localStorage / sessionStorage.
    • 
      
  • No text inside SVG; no HTML actors floating over an SVG scene.
    • 
      
  • Draw-in strokes are invisible before they animate (opacity gate, not dash math alone).
    • 
      
  • Every drag, slider or arrow-key widget carries data-capture.
    • 
      
  • data-build and .reveal never on the same element.
    • 
    

    
    
      
  • No hand-edited board colours; no rebuilding a retired look.
    • 
      
  • One motion law; hidden depth never reflows the scene.
    • 
      
  • Never reuse an exemplar's illustration subject.
    • 
      
  • Don't pad slides past the reading-time budget.
    • 
      
  • Teaching decks always have the challenge pair and the question set; presentation decks never do.
    • 
      
  • The revisited challenge is the same problem, never a new one.
    • 
      
  • Roadmaps change only through research, or a proposal you approved. Read NOTES.md before every roadmap lesson.
    • 
      
  • Never touch repo files that aren't the skill's own.
    • 
    

  







  rulebooks/
  
The rulebooks

  
Two optional companion files for one specific, demanding job: turning university lecture slides (PDF or PPTX) into a deck that a student can study instead of the slides, ending with a self-marking quiz. You attach them to your request; they add to the skill and, where they say so, override it.


  

    

      rulebooks/slides-rulebook.md · v1.7
      
Slides Rulebook

      
How to turn one lecture into one deck that is complete, shorter to read than the slides, in plain English (A2–B1), split into topics that each stand alone, taught with research-backed methods, and phone first. It also keeps every deck of a course consistent, from the first lecture to the last.

      
Read it on GitHub ↗

    

    

      rulebooks/questions-rulebook.md · v1.2.1
      
Questions Rulebook

      
How to add a final quiz to a deck: about 10 minutes, several kinds of questions, marked on the page with a reason for every answer, and a score slide that sends you back to the topics you missed. Works with the slides rulebook or on its own, for any subject.

      
Read it on GitHub ↗

    

  


  
How to use them

This is the first deck of a new course: ask me the canvas and board before building.

  
Later decks of the same course — also attach the newest deck of the course (its code and choices are reused):

  
prompt · later deck


/lesson-deck-builder
Follow slides-rulebook.md for the attached lecture, and end the deck with a final quiz following questions-rulebook.md. Read the attached notes before planning. The newest deck of this course is attached.

  
Quiz only — for any existing deck: Add a final quiz to the attached deck, following questions-rulebook.md.

The attachments decide the case: A first deck of a course (asks the canvas gate and exam focus once), B a later deck (reuses the newest deck as the "shell" and asks only what's new), C decks of another course attached (settings don't carry over).


  
The six goals of the slides rulebook

  

    
GoalMeaningHow it's checked

    
      
G1 Replace the slidesEvery fact taught at full strength; definitions in the slides' own wordsFact ledger at 100% + a clean independent check

      
G2 English at A2–B1Everyday words, short sentencesplain_check.py: ≥98% known words, no sentence over 20 words

      
G3 Independent topicsAny topic understood alone; no unexplained wordGloss and acronym checks; a "cold read"

      
G4 Best ways to teachThe Concept Pattern and teaching rules TE1–TE10Checklist

      
G5 Shorter than the slidesFewer slides (≈0.8×) and no more words than the sourceWord budget

      
G6 Phone firstWorks upright on a phone, unchanged on a laptopChecks at 390×844, 360, 320 and sideways

    
  

  
When rules conflict: correctness first, then completeness (the word budget gives way to it), then the budget, then understandability, then teaching method, then style.


  
What's inside each file

  

    
Slides rulebook
    
      
  • Workflow W1–W11: read every page (text and images), measure the source's words, build a fact ledger, research every key concept, order for learning, plan, confirm only real decisions, write a term sheet, draft, build, check, deliver, update notes.
    • 
      
  • Rule families with IDs you can cite in feedback: L (language), T (terms), TE (teaching), F (fidelity), V (visuals), M (phone), N (navigation), Q (checks).
    • 
      
  • The Concept Pattern: ask · plain idea + case · name it · picture · why it works · worked example · common mistake · check.
    • 
      
  • Settings (§11): vocabulary level, Arabic support, deck shape, budget, quiz on/off, glossary, navigation, exact wording…
    • 
      
  • Appendices: plain_check.py (language/budget checker), topic bar, glossary, phone layer code, and the independent checker's brief.
    • 
    

    
Questions rulebook
    
      
  • Goals QG1–QG5: answerable from the deck alone, fair but challenging, ≈10 minutes, covers every topic, marks itself and teaches.
    • 
      
  • Method: list what the deck teaches by kind of knowledge, match each to the best question kinds, pick 6–9 kinds, about 2 items each.
    • 
      
  • Nine proven kinds: Choose one · True or false · Fill the gap (word bank) · Match · Put in order · Sort into groups · Find the mistake · Work it out · Label the figure. Plus six ready-to-build kinds and a list of rejected ones (with reasons).
    • 
      
  • Layout: intro slide, one slide per kind, a live score slide with "Revisit" buttons per missed topic, and "Try the quiz again".
    • 
      
  • Appendices: markup, CSS and script for every kind, a Playwright browser walk, and a worked example.
    • 
    

  


  
Records kept inside each deck

  
Rulebook decks carry their own paper trail as HTML comments (invisible, ignored by the validator):

  

    
CommentWhat it holds

    
      
<!-- COURSE -->The course's standing choices: canvas and board, exam focus, settings, field words, deck number. Later decks copy it, so nothing is asked twice.

      
<!-- BUDGET -->The source's word count (text + words inside figures).

      
<!-- FACT-LEDGER -->Every fact of the lecture, by page, with where the deck teaches it.

      
<!-- SOURCES -->The research behind the deck: fidelity checks, misconceptions, slide errors.

      
<!-- QUIZ-MAP -->Each quiz item: kind, answer, source page, topic.

      
<!-- INDEPENDENT-CHECK -->Each pass of the separate checker agent and what it found, until it found nothing.

    
  


  
Tools the rulebooks may usePython 3 for validate.py and plain_check.py (it needs pip install wordfreq and downloads the free CEFR-J word list on first run). Optional: pdftotext and tesseract for counting the source's words, and Playwright for the quiz's browser walk. If code can't run, Claude says so in the report instead of inventing numbers.

  Questions
  
FAQ

  
Do I need to know HTML or code?
No. You talk to Claude; it writes the file. HTML only matters if you want to edit a deck by hand.

  
Why does Claude ask questions before building?
Three answers are required: the confirmed topic (a mis-aimed topic spoils every slide), the canvas, and the language. Say them in your first message to skip the questions; the topic is still confirmed in one line.

  
Does a deck work offline?
Yes, except the fonts, which load from Google Fonts. Offline, the deck falls back to your system fonts and keeps working.

  
Can I get a PowerPoint file?
Not from this skill. It makes HTML decks. Use a PowerPoint (.pptx) skill if you need a native slide file.

  
How do I share a deck?
Send the .html file, or put it on any static host (GitHub Pages, Netlify, a school site). It opens on phones too.

  
Can I change a deck after it's made?
Yes: ask Claude ("switch to the Midnight blue board", "make slide 6 a comparison", "shorter"). By hand, edit only between the BEGIN SLIDES / END SLIDES markers, keep exactly one slide active, never touch the engine script, and run validate.py.

  
Which languages are supported?
Arabic (right to left) and English (left to right), with fonts and layout tuned for each. Bilingual lessons use one as the base and mix in the other.

  
Where are Playroom, Nocturne, Terra and Classic?
Retired in v1.3. Sketchbook is the only look now. Their useful mechanics (tray, footnotes, duo panes, token journey, spotlight, smudge panels…) were redrawn in Sketchbook as components §32.

  
Arrow keys flip slides while I type in the answer box.
That deck has an old engine. Current decks ignore navigation keys inside text fields, and validate.py flags any deck without that guard. Copy a fresh engine from assets/template.html.

  
The validator says "more than 20 slides". Is that an error?
No, it's a note (⚠), not a problem (✗). It warns that a normal deck may be over the 30-minute budget. Rulebook lecture decks are expected to trigger it.

  
Can I add my own chalkboard board?
Yes, as a change to the skill. style-system.md §5 lists the tuning rules every board must meet (lightness, chalk colour, contrast, pen saturation) and every file that lists the boards.

  
Do I have to use the rulebooks?
No. They are only for turning lecture slides into study decks. For everything else, the skill alone is enough.
